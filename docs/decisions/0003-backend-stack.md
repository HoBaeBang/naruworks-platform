# ADR 0003 - 백엔드 스택 — axum + sqlx + utoipa

## 결정

Rust 백엔드는 웹 프레임워크로 `axum` 0.8.x, 비동기 런타임으로 `tokio` 1.x를 사용한다. PostgreSQL 접근은 `sqlx` 0.8.x로 하고, 스키마 변경은 `sqlx migrate`로 관리한다. OpenAPI는 `utoipa` 5.x로 생성하고, 관측과 HTTP 미들웨어에는 `tracing`과 `tower-http`를 사용한다.

스파이크의 `Cargo.lock` 해석값은 `axum` 0.8.9, `axum-core` 0.5.6, `sqlx` 0.8.6, `utoipa` 5.5.0, `tokio` 1.54.1, `hyper` 1.12.0, `tower` 0.5.3이다. 이 값은 스파이크 재현을 위한 참고값이며 이 ADR에서 고정(pin)하지 않는다.

프런트엔드는 이 ADR 범위 밖이다. 디자인 시안이 확정된 뒤 별도로 평가한다.

## 배경

나루 드라이브의 파일 업로드 한도(NFR-PERF-002)를 검증하기 위해 파일당 1GB는 [DEC-086](../01-planning/02-decision-log/decision-log.md)에서 1,073,741,824 B로 확정했다. 04 문서는 업로드당 서버 메모리 증가 ≤64 MiB(PV-003)를 제안한다. 응답 시간과 동시 접속 요구(NFR-PERF-003·004)에 대해서는 동시 20명에서 목록·메타데이터 API p95 ≤300 ms(PV-008·009)를 제안한다.

통합 로그아웃과 정지 회원의 세션 처리(NFR-SEC-001·002), 비회원 공유 링크 보호(NFR-SEC-003)를 지원해야 한다. 로그 보관과 마스킹은 NFR-OPS-002와 PV-016을 따른다. 통합 인증 구현 방식은 DEC-008에서 설계로 이관됐으며, IdP와 세션 정책은 미결이다(GAP-028).

06F는 스트리밍, IdP 수용성, API 성능, PostgreSQL 접근, OpenAPI와 관측성 등을 기준으로 후보를 평가했다. Mac 스파이크에서 axum과 actix-web의 업로드와 OpenAPI를 실측했다. 재채점 결과는 같았고, 06F의 가중치와 점수는 설계 제안값이다.

## 이유

axum의 Tower 계층에서 인증·레이트 리밋·요청 로깅을 공통 미들웨어로 구성할 수 있다. 라우터와 미들웨어 계층은 특정 IdP에 종속되지 않아 DEC-008에서 어느 방식을 선택해도 사용할 수 있다.

sqlx로 PostgreSQL 질의를 SQL로 직접 작성해 인덱스와 시각 경계 요구를 표현할 수 있다(PV-011·020). `query!`를 이용한 컴파일 타임 검사와 `#[sqlx::test]`를 이용한 실제 PostgreSQL 시험이 가능하다. 스파이크에서는 `query_as` 컴파일만 확인했다. `query!`와 PostgreSQL 대상 실행은 [미확인]이다.

Mac 스파이크는 단일 업로드의 청크를 순차로 전송했다. A(axum)와 B(actix-web) 모두 1 GiB(1,073,741,824 B)를 저장했고, 원본과 저장본의 SHA-256이 일치했다. 마지막 청크에 1 B를 더 보낸 요청은 `Content-Length` 지정과 `Transfer-Encoding: chunked` 두 방식 모두 HTTP 413을 반환했다. 129번째 청크로 1 B를 보낸 경우도 HTTP 413을 반환했다. 두 조합 모두 OpenAPI 3.1.0 JSON의 파싱과 업로드 경로·응답을 확인했다.

| Mac 실측 항목 | A axum | B actix-web |
|---|---:|---:|
| 서버 RSS 증가(상한 65,536 KiB) | 5,712 KiB | 4,768 KiB |
| 클린 release 빌드 | 18.71초 | 22.61초 |
| 증분 release 빌드 | 1.71초 | 2.05초 |
| release 바이너리 | 1,966,192 B | 5,577,216 B |

### 검토한 대안

- **actix-web + sqlx**는 단일 업로드와 OpenAPI 시험을 axum과 동등하게 통과했다. Tower 미들웨어와 직접 호환되지 않아 인증·관측 미들웨어를 전용으로 구성해야 한다(06F §4.1·§7.1). 바이너리 크기와 빌드 시간은 참고값으로 비교했다.
- **sea-orm + sea-orm-migration**은 CRUD 작성에 유리하다. 공유·재귀 폴더·시각 경계 질의에서 ORM 추상화를 벗어나 SQL을 직접 작성할 수 있고, 마이그레이션에서 부분 인덱스 같은 PostgreSQL 기능의 표현이 장황해질 수 있다. 컴파일 타임 SQL 검사는 06F에서 sqlx의 선택 근거로 제시했다. sea-orm에서의 지원 여부는 06F에 근거가 없어 [미확인]이다(§4.2·§4.3).
- **diesel + diesel-async + refinery**는 동기식 diesel에 별도 `diesel-async`를 조합해야 한다. 학습 곡선이 가파르고, DB 접근과 마이그레이션에 도구를 각각 구성해야 한다(06F §4.2·§4.3·§9).
- **aide**는 axum 핸들러 시그니처에서 명세를 추론하며 커스텀 extractor마다 트레이트 구현이 필요하다. utoipa는 Mac 스파이크에서 OpenAPI JSON 생성을 확인했다(06F §4.4·§6).

## 결과

- axum이 0.x 계열이므로 0.x의 마이너 버전 변경에도 호환성이 깨질 위험이 있다. 버전을 올릴 때 API와 Tower 계층의 호환성을 확인한다. 크레이트 유지보수·라이선스·취약점 이력과 CI 빌드 재현성은 [미확인]이다(06F §8 RK-002·003).
- Mac 실측의 범위는 단일 업로드와 로컬 루프백이다. 동시 부하, PostgreSQL 실행, 프록시·TLS 경유는 [미확인]이다(06F §8 RK-001).
- `query!`를 도입하면 PostgreSQL과 `sqlx-cli`로 `.sqlx` 오프라인 메타데이터를 생성하고 갱신해야 한다. CI 컴파일은 PostgreSQL에 연결하거나 생성된 메타데이터를 사용한다. 필요한 권한은 도입 시 PostgreSQL 설치·실행 및 `sqlx-cli` 설치 승인이다(06F §6.1·§8 RK-008).
- 구조화 로그의 토큰·이메일 원문 유출 위험은 마스킹과 로그 필드 제한으로 줄인다(06F §8 RK-010, PV-016). 세션 관련 세부 기준은 인증/IdP ADR 이후에 조정할 수 있다(RK-004).

### 후속 확인

- [ ] 1 GiB 1건과 100 MiB 2건을 동시에 업로드하여 업로드당 서버 RSS 증가가 64 MiB 이하인지 확인한다(PV-003·009).
- [ ] 동시 20명(20 VU) 부하에서 목록·메타데이터 API p95가 300 ms 이하인지 확인한다(PV-008·009).
- [ ] 실제 PostgreSQL에서 `#[sqlx::test]`로 마이그레이션 적용과 `query_as` 실행을 검증하고, `Clock`을 주입해 시각 경계 시험을 수행한다(06F §6.1·§7.2).
- [ ] `sqlx query!`의 컴파일 타임 검사는 2026-11-19 호배님 결정으로 당분간 제외한다. 재개 시 `.sqlx` 메타데이터와 잘못된 SQL을 거부하는 시험을 확인한다(06F §6.1·§8 RK-008).

후속 시험 결과가 합격 기준에 미달하면 이 ADR을 재검토한다.
