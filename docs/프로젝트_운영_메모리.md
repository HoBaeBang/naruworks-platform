# NaruWorks 프로젝트 운영 메모리

이 문서는 Codex가 새 대화에서 NaruWorks 프로젝트를 이어받기 위해 가장 먼저 읽어야 하는 운영 메모리입니다.

## 프로젝트 정체성

NaruWorks는 개인 홈서버 위에서 여러 웹/앱 서비스를 운영하기 위한 개인 브랜드 서비스 플랫폼이다.

핵심 메시지:

```text
기획 -> 프론트엔드 -> 백엔드 -> 데이터베이스 -> CI/CD -> 홈서버 운영까지 직접 수행하는 end-to-end 포트폴리오 플랫폼
```

이 프로젝트는 단순 landing page가 아니다. `Naru`라는 브랜드 아래에서 내가 필요하고 만들고 싶은 서비스를 직접 제공하는 장기 운영 플랫폼이다.
방문자는 Naru 홈에 들어와서 여러 기능과 서비스를 선택해 사용할 수 있어야 한다.
서비스 아이디어는 외부 요청을 받아 정하는 것이 아니라, 내가 정하고 직접 만든다.

StablePay는 Go 기반 결제/원장/정산 기준 구현이다.

NaruWorks에서는 StablePay를 아래 중 하나로 연결한다.

```text

2. stablepay-adapter service 작성
3. 나중에 Spring Boot payment module로 재구현
```

현재 판단:

```text
StablePay를 NaruWorks 안에 바로 합치지 않는다.
먼저 독립 결제 도메인 기준 구현으로 유지한다.
NaruWorks는 플랫폼/운영/서비스 허브 역할을 맡는다.
```

6. 문서는 새 대화에서도 이어받을 수 있게 항상 현재 상태를 기록한다.

## Naru 서비스 방향

NaruWorks의 중심은 `Naru` 브랜드 포털이다.

```text
Naru Home
-> 내가 운영하는 서비스와 기능으로 들어가는 브랜드 첫 화면
-> 프로젝트 소개만 하는 포트폴리오가 아니라 실제 서비스를 사용하는 입구
```

초기 서비스 로드맵:

```text
1. Naru Calendar
   - Google Calendar처럼 동작하는 일정관리 서비스
   - 1단계 목표는 자체 일정 CRUD와 Google Calendar 일정 동기화 가능성 검토

2. Naru Drive
   - 개인 파일 저장/관리 서비스

3. Naru Docs / Sheets / Slides
   - Google Docs, Sheets, Slides와 유사한 문서/스프레드시트/발표자료 기능
```

관리자 화면은 그 자체가 목표가 아니다.
필요한 경우 각 서비스를 운영하기 위한 최소 관리 기능만 만든다.

## Backend 코딩 컨벤션

초기 backend는 Gradle 멀티 모듈 구조를 기준으로 한다.

```text
naru-api
= Spring Boot 실행 애플리케이션, Controller, Request/Response DTO, API 예외 처리

naru-core
= Service, 트랜잭션 흐름, 도메인 객체 조합, repository/adapter 호출

naru-domain
= 핵심 도메인 model, enum type, 필요 시 value object

naru-infrastructure
= JPA, PostgreSQL repository 구현, 외부 API adapter, StablePay adapter
```

의존성 방향은 아래를 기본으로 한다.

```text
naru-api -> naru-core -> naru-domain
naru-infrastructure -> naru-core, naru-domain
```

Request/Response는 API DTO로 부르고 Java record를 우선 사용한다.

```text
ProjectResponse, CreateProjectRequest 같은 이름을 사용한다.
DTO 변환 메서드는 다른 객체에서 변환할 때 from(...), 값으로 생성할 때 of(...)를 사용한다.
```

Java 객체 형태 컨벤션은 아래를 기준으로 한다.

```text
API Request DTO
= record 기본

API Response DTO
= record 기본

Domain Model
= class 기본
= id, 상태, 상태 전이, 도메인 규칙을 가진 비즈니스 대상
= 예: Member, CalendarEvent, Project, ServiceCatalogItem

Value Object
= record 우선
= id 없이 값 자체가 의미이며 불변이어야 하는 도메인 값
= 예: Email, TimeRange, CalendarEventColor, ProjectSlug

JPA Entity
= class

Enum Type
= enum
```

Domain Model과 Value Object 판단 기준:

```text
Domain Model
= 고유 id를 가질 수 있다.
= 상태가 시간에 따라 변한다.
= 조회/수정/삭제의 중심이 된다.
= 다른 객체와 관계를 맺는 중심이다.
= 비즈니스에서 주요 대상으로 부르는 명사다.

Value Object
= id 없이 값 자체로 구분된다.
= 불변이어야 한다.
= 값 검증 규칙을 품는다.
= primitive string/number로 두면 의미가 흐려진다.
= 여러 도메인 모델에서 재사용될 수 있다.
```

Lombok은 초기부터 사용한다.

```text
Controller, Service 등 Spring bean의 생성자 주입은 @RequiredArgsConstructor를 우선 사용한다.
DTO와 단순 값 객체는 Lombok class보다 Java record를 우선 사용한다.
JPA Entity는 도입 시점부터 Lombok을 적용하되, 무분별한 @Data 사용은 피한다.
JPA Entity에는 setter를 만들지 않는다.
JPA Entity 필드에는 해당 필드가 무엇을 의미하는지 주석을 작성한다.
DB 테이블/컬럼 의미는 Flyway migration의 COMMENT ON TABLE/COLUMN으로 남긴다.
```

VO는 API Request/Response가 아니라 도메인 Value Object를 뜻한다.

```text
예: ProjectSlug, Email, Money
```

## 인증/인가 방향

NaruWorks는 개발자 본인뿐 아니라 지인도 함께 사용하는 개인 서비스 플랫폼이므로 회원가입과 로그인이 필요하다.
초기 인증/가입 방향은 유효한 초대 코드 + Google 로그인 + 약관 동의 기반 자동 승인 방식으로 정한다.
장기 인증/인가 구조는 frontend proxy 중심이 아니라 `api.naruworks.com`을 공개 backend API 진입점으로 두고 Spring Security가 인증/인가를 책임지는 방식으로 잡는다.

```text
app.naruworks.com -> frontend
api.naruworks.com -> backend
```

```text
유효한 초대 링크 또는 추천 코드 확인
-> Google 로그인
-> 약관 동의
-> 내부 회원을 처음 생성
-> 일반 초대 회원은 APPROVED 상태로 즉시 이용
-> 관리자는 회원 조회·정지·초대 코드 운영을 수행
```

회원 상태:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

권한:

```text
USER
ADMIN
```

CalendarEvent는 member_id를 가져야 하며, 각 사용자는 자기 일정만 조회/생성/수정/삭제할 수 있어야 한다.

## 추천 및 초대 정책

추천 관계는 자유 텍스트 추천인명으로 남기지 않고, 기존 회원을 직접 참조하는 관계로 관리한다.

```text
members.referrer_member_id
= 가입자를 초대한 기존 회원의 members.id

members.referral_code
= 승인 회원에게 발급되는 고유 추천 코드
= 영문 대문자와 숫자로 구성된 6자리 값 (예: AB12CD)

초대 링크
= https://app.naruworks.com/join?ref={referralCode}
```

사용자 경험은 초대 링크를 기본으로 하고, 추천 코드 직접 입력은 링크를 받지 못한 경우의 보조 수단으로 제공한다.
초대 링크 또는 추천 코드가 없는 신규 사용자는 Google 로그인을 시작할 수 없다.

```text
초대 링크 접속
-> 유효한 추천 코드인지 확인
-> Google 로그인 전 backend HttpSession의 naru.pending-referral-code에 임시 보관
-> Google 로그인 성공 후 /join/terms 이동
-> 약관 동의 API 성공 시 referral_code로 추천 회원을 찾아 Member를 처음 생성
-> APPROVED 상태로 Calendar 등 서비스 이용
```

초기 정책:

```text
추천인은 APPROVED 회원만 될 수 있다.
회원당 추천인은 한 명만 연결한다.
초대 코드와 약관 동의로 생성된 일반 회원은 USER + APPROVED 상태가 된다.
추천 관계는 회원 생성 시 한 번만 설정하고 이후 변경하지 않는다.
추천 코드와 초대 링크는 추천 관계의 정확한 추적을 위한 수단이다.
추천 코드는 OAuth state가 아니라 별도 HttpSession attribute에 보관한다.
초대 코드 없이 일반 Google 로그인한 신규 사용자는 session을 종료하고 /join?error=invitation-required로 이동한다.
최초 운영자는 NARU_INITIAL_ADMIN_EMAIL과 Google email이 같고 members 테이블이 비어 있을 때만, 약관 동의 후 ADMIN + APPROVED로 생성한다.
최초 운영자 생성이 끝나면 NARU_INITIAL_ADMIN_EMAIL 환경변수는 운영 환경에서 제거한다.
초대 코드 검증 API에는 rate limit을 적용하고, 추후 추천 코드 재발급·폐기 기능을 제공한다.
```
