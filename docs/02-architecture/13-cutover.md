## 1. 전환 원칙

- **[기획]** 설계서 23장에 따라 기존 Java 서비스에서 새 Rust 서비스로 전면 교체한다. 병행 운영은 없다. 기획에서 전환 방식을 바꾸면 이 절차를 개정한다.
- **[기획]** 기존 회원·파일 등 DB 데이터는 이관하지 않고 새 PostgreSQL에서 시작한다. ADR 0004에 따라 Keycloak과 전용 DB를 새 구성에서 제외하고, 나루가 Google 로그인에 직접 연결해 PostgreSQL에서 회원 상태와 세션을 관리한다. 구 스택과 Keycloak은 롤백에 대비해 보존한다. [PRD §7](../01-planning/prd/PRD.md) · [서비스 정의 §5](../01-planning/00-context/service-definition.md#5-이월-항목-위치만-참조) · [ADR 0004](../decisions/0004-auth-idp-litpage.md)
- **[제안]** 아래는 전환 체크리스트다. 06F AS-A4의 단일 서버 가정을 사용한다. 배포 토폴로지와 IaC는 [미확인]이다. [05 아키텍처](05-architecture.md) · [06F §11.3](06F-stack-feasibility.md#113-가정-목록)

## 3. 단계별 전환 절차

### 3.1 사전 점검

- [ ] **[제안]** 대상 릴리스로 비운영 스택을 준비한다. 빈 PostgreSQL에 구현 마이그레이션을 순서대로 적용하고 초기 카테고리·서비스 배정이 시드로 갖춰지는지 확인한다. 08의 SQL은 문서용 초안이다. 시드 주입 방식·시점과 초기 Litpage 노출값은 [미확인]이다. [08 버전 관리와 시드](08-db/08-db-schema.md#버전-관리와-시드) · [06 크레이트 구조](06-crate-layout.md) · [ADR 0003](../decisions/0003-backend-stack.md)
- [ ] **[제안]** 대상 빌드의 Rust 포맷·정적 검사·워크스페이스 시험, 빈 PostgreSQL 스키마 적용, OpenAPI 린트, 이미지 빌드 결과를 확인한다. 내부 준비 상태와 외부 사용자 경로를 확인할 수단을 마련한다. 배포 호스트·이미지 레지스트리·런타임 시크릿 위치는 [미확인]이다. [10 §5·7·9](10-observability-ci.md#5-헬스체크)
- [ ] **[제안]** CO-01~03 설정의 존재와 적용·복귀 가능 여부를 각 보관 위치에서 확인한다. 구 Java 스택·Keycloak 및 전용 DB, 구 Litpage 인증 구성으로 복귀할 수 있어야 한다. 단일 서버에서 구 스택을 보존하면서 새 스택을 기동할 수 있는 자원과 포트 배치, 필요 시 구 Java 서비스만 격리했다가 복귀시키는 방법은 [미확인]이다.
- [ ] **[제안]** Litpage의 새 RP와 나루 OP를 함께 준비한다. OP 엔드포인트는 07의 B-1 표와 OpenAPI를, 등록된 HTTPS 콜백·로그아웃 복귀 URI·백채널 수신 주소 및 나루·Litpage의 별도 세션은 09의 계약을 따른다. 기존 Keycloak RP 코드와 기존 로컬 세션의 인증 연결을 재사용하지 않는다. [07 B-1 계약](07-api/07-api.md#litpage-b-1-oidc-계약) · [OpenAPI](07-api/openapi.yaml) · [09 §3~5](09-auth.md#3-세션-수명갱신회원-정지) · [ADR 0004](../decisions/0004-auth-idp-litpage.md)
- [ ] **[기획]** 월 가용률 목표는 99%다. 미리 알린 점검과 Google·Cloudflare 등 외부 장애는 계산에서 제외하고 출시 후 한 달 동안 관찰한다(DEC-089). **[제안]** 점검 창, 롤백에 필요한 여유, 결정 담당자를 정하고 사용자에게 전환 시점과 기존 데이터 미이관을 미리 알린다. 공지 시점·방법과 롤백 창의 종료 조건·시각은 [미확인]이다. [NFR-AVAIL-001](../01-planning/nfr/NFR.md) · [DEC-089](../01-planning/02-decision-log/decision-log.md) · [04 §4.6](04-NFR-technical.md#46-nfr-avail-001--월-허용-중단-시간)
- [ ] **[제안]** §4 리허설 결과와 §3.4 합격 증적을 확인한다. 필수 확인이 남거나 복귀 경로를 검증하지 못했으면 운영 전환을 보류한다.

### 3.2 동결

- [ ] **[제안]** 사전 점검 통과 후 공지한 전환 창에 점검 상태로 들어가고, 기존 Java 서비스의 쓰기와 신규 가입을 동결한다. 전환 중에도 구 서비스에 새 데이터가 쌓여 사용자가 혼동하는 일을 막기 위한 조치다.
- [ ] **[제안]** 동결 적용과 진행 중이던 쓰기의 종료를 확인한 뒤 사용자 트래픽을 구 서비스에서 차단한다. 새 서비스는 §3.4 검증에 필요한 접근만 열어 둔다. 동결·점검 노출의 적용 방법은 [미확인]이다.

### 3.3 전환

**[제안]** 동결을 확인한 뒤 다음 순서로 진행한다. 일반 사용자에게는 §3.4를 통과한 뒤 개방한다.

1. [ ] 빈 PostgreSQL을 대상으로 새 Rust 스택을 기동한다. 검증된 초기 스키마와 시드를 적용해 초기화하고 내부 준비 상태를 확인한다.
2. [ ] Cloudflare 대시보드에서 새 Rust 원본 연결과 프록시·터널 경로(CO-02)를 적용한 뒤 도메인·DNS(CO-01)가 새 경로를 가리키게 전환한다. 외부에서 이름 해석, HTTPS 연결, 새 원본 도달을 확인한다.
3. [ ] Google Cloud Console에서 결정된 CO-03 클라이언트와 redirect URI 등록을 적용하고 나루 런타임 설정에 연결한다. 전환한 HTTPS 오리진과 09 §1의 Google 콜백 경로가 등록과 일치하는지 확인한다. [09 §1](09-auth.md#1-google-로그인과-co-03)
4. [ ] 새 나루의 Google 로그인과 OP 도달을 확인한 뒤 새 Litpage RP를 나루 OP에 연결한다. RP 등록·리다이렉트·세션·정지·로그아웃 확인은 09 §3~5 및 07의 B-1 계약을 사용한다. Keycloak은 새 인증 경로에서 제외한다. 구 Keycloak과 전용 DB의 중지·제거는 롤백 창 종료 뒤로 미룬다. [09 §4·5](09-auth.md#4-litpage-sso) · [07 B-1 계약](07-api/07-api.md#litpage-b-1-oidc-계약)

### 3.5 되돌리기 기준과 절차

**[제안]** 전환에 실패하거나 §3.4의 필수 확인이 실패하고 롤백을 시작해야 할 시점까지 해소되지 않으면 되돌린다. Google 로그인·Litpage 진입 또는 저장이 불가하거나 정지 차단·통합 로그아웃이 실패하면 사용자에게 개방하지 않는다. 개방 뒤 롤백 창 안에 같은 장애를 발견해도 이 기준을 적용한다.

1. [ ] 점검 상태를 유지하거나 다시 적용한다. 새 서비스의 쓰기와 가입을 잠그고 사용자 트래픽을 차단한다. 판정 시각과 실패 항목을 값 없이 기록한다.
2. [ ] 보존한 구 Java 스택과 Keycloak·전용 DB, 구 Litpage의 기존 인증 구성이 사용 가능한지 확인한다. 구 인증 경로가 복귀에 필요한 상태인지 내부에서 점검한다.
3. [ ] Cloudflare 대시보드에서 CO-02 프록시·터널의 원본과 CO-01 도메인·DNS 경로를 구 Java 스택으로 되돌린다. CO-03 클라이언트나 redirect URI 등록을 변경했으면 Google Cloud Console에서 구 설정을 복구한다. 두 경로 모두 확인될 때까지 점검 상태를 유지한다.
4. [ ] 외부 경로가 구 서비스만 가리키고 구 로그인·Litpage 진입이 되는지 확인한다. 구 서비스에서 쓰기·가입 동결을 해제하고 정상화 사실을 알린다.
5. [ ] 새 DB는 별도로 보존한다. 구 데이터를 신 서비스에 복원하거나 두 DB를 합치는 단계는 없다. 개방 뒤 롤백한 경우 새 서비스에서 발생한 쓰기·가입은 자동으로 구 서비스에 반영되지 않는다. 해당 기록의 후속 처리와 안내는 [미확인]이다.

## 4. 전환 리허설

**[제안]** 스테이징 또는 동등한 비운영 환경에서 §3과 같은 순서로 진행한다. 실제 리허설 호스트는 [미확인]이다. 테스트용 서비스·DB·DNS 경로·OAuth 등록을 사용하고 운영 대시보드 설정, 운영 데이터 및 실제 사용자 트래픽은 변경하지 않는다.

1. [ ] 구 동작을 재현한 검증 환경과 새 릴리스·빈 PostgreSQL을 준비한다. CI 결과와 초기 스키마·시드, 테스트용 CO 대응 설정 및 새 Litpage RP를 확인한다.
2. [ ] 공지·동결을 모의하고 구 환경의 테스트 쓰기·가입 및 사용자 경로가 닫히는지 확인한다. 새 스택 초기화·준비 확인 → 테스트 Cloudflare·DNS 경로 교체 → Google 클라이언트·콜백 적용 → 새 Litpage RP 부착 순으로 진행한다.
3. [ ] §3.4 표와 동일한 기준으로 확인한다. 만료 경계는 04·09의 주입 시계 시험 결과로 확인한다. 프록시 경유 업로드는 운영 예정 경로와 동등한 조건에서 확인하며, 동등성이나 RB-017 판정이 남으면 해당 항목을 미검증으로 남긴다.
4. [ ] 별도 회차에서 Google 콜백 불일치 또는 Litpage RP 미연동을 재현해 실패를 감지하고 §3.5를 수행한다. 구 경로와 구 로그인·Litpage 복귀, 동결 해제, 점검 안내까지 확인하고 전환·롤백 소요 시간을 기록한다.
5. [ ] 모든 §3.4 필수·채택 항목의 통과, 구 경로 복구 확인, 계획된 전환 창 안의 복귀, 비밀 값 없는 증적을 갖추면 합격으로 기록한다. 실패와 미검증 항목을 정리하고 조치 후 해당 경로를 재검증한다.
