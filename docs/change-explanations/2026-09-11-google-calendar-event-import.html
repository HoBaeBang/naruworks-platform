01 · Background

연결 정보와 일정 원본은 다른 데이터다

앞 단계에서 회원은 자신의 Google 계정을 연결하고, 그 안의 캘린더를 여러 개 선택할 수 있게 됐다. 하지만 calendar_integrations에는 OAuth 연결과 암호화된 refresh token만 있고, 실제 Google 일정은 아직 Naru Calendar 화면에 없었다.

핵심 경계. NaruWorks 내부 일정은 사용자가 생성·수정·삭제한다. Google 일정은 현재 단방향으로 읽기만 한다. 따라서 두 데이터를 같은 calendar_events 테이블에 섞으면 누가 수정 권한을 갖는지 흐려진다.

새 external_calendar_events 테이블은 Google에서 읽은 값의 저장본이다. 외부 API가 잠시 실패해도 마지막 저장 결과를 표시할 수 있고, API 응답의 source=GOOGLE, readOnly=true로 프론트가 수정 UI를 열지 않는다.

02 · Intuition

한 번의 화면 조회가 두 종류의 일정을 합친다

GET /api/calendar/events?from=&to=가 호출되면 내부 일정 발생 회차와 외부 Google 일정을 시작 시각 순으로 병합한다. 아래 단계를 눌러 데이터 이동을 따라가 볼 수 있다.

Calendar 화면은 조회 기간을 backend로 보낸다.

Before

조회 후 INSERT

동시에 두 요청이 “기존 행 없음”을 확인하면 두 INSERT가 경쟁한다. 뒤늦은 요청은 unique 제약 위반으로 실패한다.

After

DB 원자 upsert

ON CONFLICT ... DO UPDATE가 존재 여부 판단과 저장을 한 SQL 문장으로 처리한다. 동일 이벤트는 하나의 행으로 수렴한다.

03 · Code

실행 흐름대로 읽기

1. Google Events 요청은 절대 URI와 RFC 3339 시간을 쓴다

GoogleCalendarOAuthAdapter.java는 이메일 같은 calendar ID를 URL 경로에 넣고, 조회 범위를 한국 시간대의 초 단위 timestamp로 보낸다. 처음에는 완전한 URL을 상대 경로 API에 넣어 https:/...가 됐고, 이후 초 없는 timestamp가 400을 유발했다.

https://www.googleapis.com/calendar/v3/calendars/{calendarId}/events
?timeMin=2026-09-01T00%3A00%3A00%2B09%3A00
&timeMax=2026-10-01T00%3A00%3A00%2B09%3A00
&singleEvents=true&orderBy=startTime

2. core는 선택된 캘린더만 읽고, 실패하면 저장본을 유지한다

ExternalCalendarEventService.java는 enabled 상태의 캘린더만 순회한다. Google 호출이 실패해도 내부 일정 조회를 막지 않고, 기존 외부 저장본을 반환한다. 이는 외부 의존성이 개인 일정 서비스 전체를 멈추게 하지 않기 위한 정책이다.

3. PostgreSQL이 중복 경쟁을 끝낸다

ExternalCalendarEventJpaRepository.java의 native query는 복합 unique key를 upsert 기준으로 쓴다. 애플리케이션 메모리에서 먼저 읽고 판단하는 것보다 DB의 제약조건을 진실의 원천으로 삼는 방식이다.

INSERT INTO external_calendar_events (...)
VALUES (...)
ON CONFLICT (calendar_integration_calendar_id, provider_event_id)
DO UPDATE SET
  title = EXCLUDED.title,
  start_at = EXCLUDED.start_at,
  end_at = EXCLUDED.end_at,
  updated_at = EXCLUDED.updated_at
