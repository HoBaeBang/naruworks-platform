# 06F 백엔드 스택 타당성 조사 (Rust)

> **범위 안내**: 본 조사는 NaruWorks 백엔드(Rust) 스택만 다룬다. **프런트엔드: 디자인 시안 확정 후 작성**한다.  
> **사실 기준**: 실시간 웹 조회가 불가하므로 로컬 문서에서 확인할 수 없는 크레이트 버전, 최신 릴리스, 유지보수 활동, 다운로드 수, 라이선스 변경 여부 등은 모두 `[미확인]`으로 표기한다. 크레이트의 설계 특성은 `(일반 지식)`으로 구분하며 단정 수치는 배제한다.

### 2.5 백그라운드 작업 선택지 (C5: 10%)

NaruWorks의 백그라운드 작업은 성격이 두 갈래로 나뉜다:
- **애플리케이션 작업**: ① 매시간 멱등 탈퇴/휴지통/미완료 조각 정리 스위퍼(PV-002, PV-020), ② 업로드 후 비동기 썸네일 생성(PV-005)
- **인프라/운영 작업**: ③ 매일 03:00 KST 백업(PV-014), ④ 일 1회 로그 로테이션·삭제(PV-016)

| 후보 | DB 기반 큐 여부 | 적합 작업 | 근거 (일반 지식) | 위험 |
|---|---|---|---|---|
| **tokio 내장** (`tokio::time::interval` + `mpsc`) | **아니오** (인메모리) | 단순 주기 스위퍼, 1차 프로토타입 | 추가 의존성 없음. 매시간 멱등 스위퍼(PV-020)는 프로세스 재시작 후 다음 주기에 복구되므로 인메모리로도 동작 가능. | 배포/재시작 시 대기 중이던 썸네일 생성 작업(PV-005) 유실. 재시도·동시성 제어·DLQ를 직접 구현해야 함. |
| **tokio-cron-scheduler** | **아니오** (기본 인메모리, 영속화 어댑터 지원 여부 `[미확인]`) | 정시 스케줄링(03:00 KST 등) | Cron 표현식과 타임존(KST) 스케줄링에 편리함. | 다중 인스턴스 배포 시 중복 실행 방지(분산 락) 별도 필요. 썸네일 같은 작업 큐 용도가 아님. 최신 지표 `[미확인]`. |
| **apalis** (예: PostgreSQL 백엔드) | **예** (PostgreSQL/Redis 등 지원) | 비동기 썸네일 생성 큐, 재시도 필요 작업 + Cron | 기존 PostgreSQL을 큐 백엔드로 활용해 별도 브로커(Redis 등) 없이 작업 영속화·재시도·동시성 제한 가능. | 큐 폴링 부하 관리 및 스키마 테이블 추가 필요. 최신 버전·안정성 `[미확인]`. |
| **인프라 분리** (systemd timer / cron / K8s CronJob + `pg_dump` + `logrotate`) | N/A (OS/인프라 레벨) | 매일 백업(PV-014), 일 1회 로그 로테이션(PV-016) | 앱 프로세스 장애·재시작과 무관하게 백업·로그 삭제를 보장하며 RTO ≤ 4시간(PV-013) 복원 절차와도 분리됨. | 앱과 별도로 인프라 설정·모니터링(26시간 미성공 경보 PV-014) 구성 필요. |

### 2.6 관측성 (`tracing` + `tracing-subscriber` + OpenTelemetry)

- **표준 조합 (일반 지식)**: `tracing`(계측 매크로 `#[instrument]`, Span/Event) + `tracing-subscriber`(JSON 포맷터, `EnvFilter`, 레이어 합성) + `tower-http::trace::TraceLayer`(HTTP 요청·응답 지연 및 `trace_id` 상관관계).
- **OpenTelemetry 연동**: `tracing-opentelemetry` + `opentelemetry-otlp` 레이어를 추가하면 외부 수집기(OTel Collector 등)로 분산 트레이스·메트릭 전송 가능(구체적 크레이트 버전 호환성은 `[미확인]`).
- **기획/04 문서 특화 요구사항 반영**:
  - **개인정보/비밀 값 마스킹(NFR-SEC-005, PV-016)**: 로그에 토큰·시크릿·원문 이메일이 남지 않도록 구조화 로그 필드 화이트리스트/마스킹 레이어 또는 커스텀 `Debug` 구현이 필수다.

## 4. 조합 추천

### 1순위 조합
- **구성**: `axum` + `sqlx` + `sqlx migrate` + `utoipa` (+ `apalis`[PostgreSQL] 또는 `tokio-cron-scheduler` + `tracing`/`tracing-subscriber` + 인프라 백업/로테이션)
- **추천 이유**:
  1. **단일 비동기 생태계 일관성**: `tokio` + `hyper` + `tower` + `axum` + `sqlx`가 같은 비동기 기반 위에서 동작해, 스트리밍 업로드(C1), `TraceLayer` 관측성(C6), 레이트 리밋(PV-019, PV-023), 세션/인증 미들웨어(C2)를 `tower` 계층으로 일관되게 조합할 수 있다.
  2. **컴파일 타임 안정성과 실제 PG 시험**: `sqlx`는 비즈니스 규칙(30일 탈퇴·휴지통 경계, 공유/링크 권한, 삭제 원장)의 정합성을 SQL 수준에서 컴파일 타임에 검증하고 `#[sqlx::test]`로 실제 PostgreSQL 시험을 자동화하기 가장 유리하다.
  3. **DEC-008 유연성**: Keycloak 유지(OIDC RP)와 자체 IdP 구현(OIDC Provider 또는 자체 세션) 어느 쪽으로 결정되더라도 `axum`의 라우터/Extractor/미들웨어 구조가 특정 인증 모델에 종속되지 않는다.

### 2순위 조합
- **구성**: `actix-web` + `sqlx` (또는 ORM 생산성 우선 시 `sea-orm` + `sea-orm-migration`) + `utoipa`
- **추천 이유**:
  1. `actix-web`은 스트리밍(`Payload`) 처리와 성능이 검증된 성숙한 프레임워크이며 `utoipa`도 공식 지원한다.
  2. 팀이 raw SQL보다 Entity/ActiveRecord 패턴을 강하게 선호한다면 `sea-orm` 조합이 초기 CRUD 개발 속도를 높일 수 있다. 다만 Tower 미들웨어 재사용성 제약(`actix-web`)과 추상화 오버헤드(`sea-orm`) 때문에 1순위 대비 후순위로 둔다.

### 스파이크(Spike)로 검증할 항목
1. **1 GiB 스트리밍 업로드 메모리 상한 검증**: `axum` `BodyDataStream`으로 8 MiB 청크 수신 및 실수신 바이트 한도(1,073,741,824 B) 강제 시 동시 3건 업로드 중 서버 RSS 증가가 **64 MiB 이하**(PV-003)로 유지되는지 실측.
2. **인증·Litpage 연동 프로토타입**: DEC-008 후보(Keycloak vs 자체 IdP) 중 선택안에 대해 ① 통합 로그아웃 전파 ≤ 5초(PV-017), ② 정지 회원의 기존 세션 유지·신규 차단(NFR-SEC-002), ③ Litpage(`services/litpage/NARU.md`) 세션/토큰 연동 동작 검증.
3. **PV-011 데이터셋 + 20 VU 부하 p95 검증**: 회원 100·폴더당 1,000항목 시드 환경에서 드라이브 목록·공유·링크 조회 API가 20 VU 부하 중 **p95 ≤ 300 ms**(PV-008)를 만족하는지 `k6`로 측정.
4. **비동기 썸네일 생성 메모리·동시성 격리**: 이미지·PDF·동영상 썸네일 생성(외부 바이너리/라이브러리 호출 포함)이 API 서버의 64 MiB/응답 예산과 충돌하지 않도록 워커 동시성 제한 검증.
5. **시계 주입 기반 30일 경계 시험**: `Clock` 트레이트 + `sqlx::test`로 탈퇴·휴지통 30×24시간 경계(PV-020) 및 세션 유휴 7일/절대 30일 경계(PV-029) 자동 테스트 검증.

## 5. 인증·IdP 연동 메모 (DEC-008 · Litpage 제약)

기획 및 기존 코드베이스에서 확인된 제약은 다음과 같다:

1. **미결 설계 이관 (DEC-008, `open-questions.md`, `GAP-028`)**:
   - 통합 인증을 **Keycloak 유지**로 갈지 **자체 개발**할지는 아직 결정되지 않았으며(호배님은 Keycloak 부적합 가능성과 자체 개발 검토 요청), 수정 Litpage 코드 재사용 여부도 함께 설계 ADR에서 결정해야 한다.
2. **현재 수정된 Litpage 코드의 결합 상태 (`services/litpage/NARU.md`)**:
   - 현재 `services/litpage/apps/server/src/oidc.ts`는 Keycloak(`naruworks` realm) OIDC(Authorization Code + PKCE)를 전제로 구현되어 있으며, `member` 역할·`email_verified` 검증 및 `idp_identities`(`sub`) 매핑을 사용한다.
   - **자체 개발 선택 시 제약**: Rust 백엔드가 표준 OIDC Provider(Authorization Code + PKCE, Discovery, JWKS, Back-Channel Logout) 역할을 직접 제공하거나, Litpage의 `oidc.ts`를 자체 인증 프로토콜에 맞게 재수정해야 한다.
   - **Keycloak 유지 선택 시 제약**: Rust 백엔드는 OIDC Relying Party + Keycloak Admin/세션 제어만 담당하면 되지만, `NARU.md`의 알려진 위험("세션 수명 7일: 정지 시 최대 7일 접속 유지")과 NFR-SEC-001(로그아웃 전파 ≤ 5초)을 만족시키기 위해 백채널 로그아웃 또는 단기 토큰 연동이 필요하다.
3. **통합 로그아웃 vs 정지 회원 기존 세션 유지의 충돌 가능성 (`GAP-034`, `PV-017`, `PV-018`)**:
   - `NFR-SEC-001`(DEC-015)을 위해 액세스 토큰 수명을 5분 이하로 두면(PV-017), 정지된 회원의 기존 세션이 토큰 갱신 시점이나 Litpage SSO 첫 진입 시 끊겨 `NFR-SEC-002`(DEC-027: 기존 세션은 로그아웃까지 나루·Litpage 모두 사용)와 충돌할 수 있다(`GAP-034`).
   - 따라서 Rust 스택의 세션/인증 계층은 **상태 유지형(Stateful) 세션 또는 백채널 로그아웃(Back-Channel Logout) 기반 무효화**를 우선 지원할 수 있어야 하며, 이는 `axum` + PostgreSQL(또는 인메모리 캐시 병행) 세션 미들웨어 구조에 유리하다.
4. **Google 단일 소셜 로그인·즉시 가입 (`DEC-005`, `DEC-007`)**:
   - 1차는 Google만 지원하며 승인 없이 즉시 가입된다. 단, 정지·탈퇴 30일 보관·복구(DEC-021, `FR-AUTH-004`) 상태 판별은 Google `sub` 또는 이메일 매핑을 통해 NaruWorks DB 상태와 결합되어야 한다.
5. **인증 관련 Rust 크레이트**: `openidconnect`, `oauth2`, `jsonwebtoken`, `tower-sessions` 등 후보 크레이트의 최신 버전·API·취약점·유지보수 현황은 `[미확인]`이다.
