01 · Background

계정과 캘린더는 다른 대상이다

Google 계정을 한 번 연결해도 기본·가족·공유처럼 여러 캘린더가 있을 수 있다. OAuth refresh token은 계정 연결의 비밀값이고, 화면에 표시할지 여부는 캘린더별 사용자 설정이다.

현재 범위. 목록을 읽고 선택을 저장한다. 선택된 Google 일정의 조회·DB 저장·Naru Calendar 화면 병합은 아직 다음 단계다.

02 · Intuition

열쇠 꾸러미와 책갈피를 분리한다

기존에는 연결 테이블에 selected_calendar_id 하나만 두었다. 이제 연결은 열쇠 꾸러미, 캘린더 선택은 책갈피처럼 따로 보관한다.

Before

한 캘린더만 선택

calendar_integrations.selected_calendar_id 하나에만 ID를 넣을 수 있었다.

Problem

다중 선택 불가

가족 캘린더를 켜면 운동 캘린더를 함께 저장할 자리가 없었다.

After

계정 연결

calendar_integrations는 암호화 refresh token과 Google 계정만 맡는다.

After

캘린더별 선택

calendar_integration_calendars가 각 ID, 이름, 색상, enabled를 보관한다.

응답의 작은 함정

Google Calendar 목록의 primary는 선택적 필드다. 일부 항목은 null을 보낼 수 있으므로 Java의 원시형 boolean 대신 Boolean으로 받고, true일 때만 기본 캘린더로 처리한다.

03 · Code

실행 순서대로 읽기

1. 데이터 모델과 migration

calendar_integrations
  = 회원 + Google 계정 연결 + 암호화 refresh token

calendar_integration_calendars
  = integration_id + provider_calendar_id (UNIQUE)
  = calendar_name + calendar_color + enabled
  = last_synced_at + sync_token (향후 일정 동기화용)

2. Refresh token으로 목록을 읽는다

목록 조회 때만 암호화 token을 복호화하고, Google token endpoint에서 짧게 쓰는 access token을 새로 받는다. access token은 DB에 저장하지 않는다.

refreshToken = decrypt(encryptedRefreshToken)
accessToken = refreshAccessToken(refreshToken)
googleCalendars = findCalendars(accessToken)

3. 저장 전 목록 검증

브라우저가 보낸 캘린더 ID를 바로 신뢰하지 않는다. 현재 Google 목록에 실제 존재하는 ID인지 확인한 뒤 enabled 상태를 저장한다.

if (!availableCalendarIds.containsAll(requestedCalendarIds)) {
  throw new IllegalArgumentException(...)
}

4. API와 화면

API역할
GET /calendarsGoogle 목록 + DB 선택 상태 반환
PUT /calendars체크된 캘린더 ID 목록 저장
아직 일정을 못 보는 이유. 이 API는 Calendar List API까지만 호출한다. 다음 단계에서 Events API를 호출해 외부 이벤트 저장소에 보관하고 기존 월·주·일 화면과 병합해야 한다.
