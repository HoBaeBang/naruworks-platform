01 · Background

코드는 늘고, 변경의 이유도 늘어난다

NaruWorks는 Calendar, 인증, Google 연동, 공유 캘린더처럼 실제 운영 기능이 늘어나는 단계다. 커밋만 남으면 “왜 바꿨는지”, “어떤 경로로 검증했는지”, “어떤 영역의 변경인지”를 나중에 빠르게 복원하기 어렵다.

가장 작은 단위의 기록. 이슈는 문제와 완료 조건, 브랜치는 구현 중인 변경, PR은 리뷰와 검증 결과, CI는 반복 가능한 통과 증거를 맡는다. 네 가지를 나누면 하나의 도구가 모든 책임을 떠안지 않는다.

이번 변경은 실제 서비스 기능이 아니라, 이후의 서비스 기능을 더 안전하고 읽기 쉽게 만들기 위한 개발 기반이다. Issue #1을 만들고 feature/NARU-1-github-workflow 브랜치에서 작업한 뒤, PR #2를 develop으로 열었다.

02 · Intuition

이슈에서 머지까지, 한 번의 짧은 루프

아래 단계를 누르면 각 단계가 남기는 정보와 다음 단계의 이유를 볼 수 있다.

Issue는 배경, 목표, 완료 조건, 검증 시나리오를 먼저 고정한다.

Before

작업 뒤에 설명을 찾는다

브랜치 목적, 테스트 범위, 변경 영역을 커밋과 대화에서 추측해야 한다. 같은 검증 명령도 사람마다 빠질 수 있다.

After

작업 전에 증거의 자리를 만든다

이슈 양식과 PR 양식이 먼저 필요한 내용을 묻고, CI가 backend와 frontend 품질 검증을 매 PR마다 반복한다.

03 · Code

실행 순서대로 읽기

1. 이슈 양식은 구현 전에 합의할 질문을 만든다

feature.yml은 작업 방식과 기능 영역을 선택하게 하고, 배경·목표·설계·검증 시나리오를 받는다. 이슈 하나의 범위를 작게 유지하기 위한 장치다.

작업 방식: 학습형 | 구현형
기능 영역: platform | calendar | auth | drive | docs | infra

배경과 문제
목표와 완료 조건
구현 설계
검증 시나리오

2. 라벨은 제목보다 구조적인 검색 키다

라벨 축예시답하는 질문
작업 유형type:feature기능인가, 릴리즈인가?
작업 방식mode:learning누가 구현하고, 리뷰에서 무엇을 볼까?
기능 영역domain:calendar어느 서비스의 변경인가?

이번 PR #2에는 type:feature, mode:implementation, domain:platform을 붙였다. 담당자는 항상 HoBaeBang으로 두고, 같은 계정으로 운영하는 현재 상황에서는 별도 reviewer 강제를 두지 않는다.

3. PR 템플릿은 리뷰자가 필요한 순서로 내용을 정렬한다

PULL_REQUEST_TEMPLATE.md는 연결 이슈, 라벨, 변경 이유, 주요 파일, API/DB/운영 영향, 검증 결과, 직접 테스트 방법, 리뷰 포인트를 남긴다. PR을 처음 보는 사람이 diff보다 먼저 “변경의 의도”를 읽을 수 있게 한다.

4. CI는 두 작업을 독립적으로 검증한다

pr-ci.yml은 develop 또는 main 대상 PR에서 두 job을 병렬로 실행한다. 하나가 실패해도 다른 job의 결과가 남아 원인을 더 빨리 좁힐 수 있다.

Backend Test
  cd backend
  ./gradlew clean test

Frontend Quality
  cd frontend
  npm ci
  npm run lint
  npm run build
관찰된 결과. PR #2는 두 번의 커밋 뒤에도 Backend Test, Frontend Quality 모두 성공했고, 충돌 없는 머지 가능 상태가 됐다.

5. 반복 확인에는 브라우저 대신 gh를 쓴다

브라우저는 GitHub Settings Ruleset 설정이나 사람이 보는 최종 diff에 유용하다. 하지만 PR 상태, 라벨, CI처럼 구조화된 정보는 gh가 더 짧고 안정적으로 읽는다. 인증 토큰은 macOS Keychain에 보관하며 커밋이나 문서에 넣지 않는다.

gh pr view 2 --repo HoBaeBang/naruworks-platform \
  --json title,state,labels,statusCheckRollup,mergeStateStatus

gh pr checks 2 --repo HoBaeBang/naruworks-platform
아직 남은 운영 설정. 문서에는 main Ruleset 기준을 정했지만, GitHub Settings에서 Ruleset을 실제로 생성하는 마지막 저장 작업은 별도로 남아 있다. Ruleset은 PR 필수, 두 CI 성공, force push·삭제 금지, 대화 해결을 요구하도록 설정한다.
