# 오픈소스 서비스 연동 기준

작성일: 2026-11-12

방향은 [ADR 0002](../decisions/0002-open-source-service-platform.md)를 따른다. 이 문서는 오픈소스 서비스를 NaruWorks에 연결하는 조건과 절차, 그리고 인증 연동 구조의 결정과 미결을 정리한다.

문서의 내용은 세 가지로 구분한다.

- **확정**: 합의했거나 코드에 이미 반영된 것
- **제안**: 추천했지만 아직 합의하지 않은 것
- **미결/미확인**: 정해지지 않았거나 확인하지 못한 것

## 1. 용어

| 용어 | 뜻 |
| --- | --- |
| 직접 서비스 | NaruWorks가 직접 만드는 서비스. 드라이브, 문서관리, Naru Calendar |
| 오픈소스 서비스 | 외부 오픈소스를 NaruWorks 회원 정보로 연동해 제공하는 서비스. 예: Litpage |
| 카탈로그 | 연동된 오픈소스 목록. 사용자가 골라 쓰고, 없으면 사용을 신청한다 |
| 연동 | 오픈소스가 NaruWorks의 로그인, 화면 규칙, 드라이브를 따르게 만드는 작업 |

## 2. 연동 조건

오픈소스를 카탈로그에 올리려면 아래를 모두 만족해야 한다.

| 조건 | 내용 | 상태 |
| --- | --- | --- |
| 라이선스 | 서비스로 제공해도 문제가 없는 라이선스여야 한다. 라이선스 고지는 원본 그대로 유지한다 | 허용 목록은 **미결** |
| 로그인 | NaruWorks 로그인(Keycloak OIDC)만 쓴다. 자체 가입과 로그인 경로는 제거한다. `member` 역할이 없으면 접근하지 못한다 | **확정** (Litpage에 적용) |
| 회원 상태 | 회원이 정지되거나 탈퇴하면 접근을 막는다. 데이터는 지우지 않는다 | 방향 **확정**, 반영 시간은 5장 |
| 화면 | 상단에 NaruWorks 로고와 서비스 이동, 회원 메뉴가 있는 바를 둔다. 하단은 NaruWorks 서비스 가이드라인에 맞춘다 | 상단 바는 Litpage에 적용, 하단 가이드라인 내용은 **미결** |
| 저장 | 사용자가 만든 결과물은 나루 드라이브에 저장할 수 있어야 한다 | 연동 방식 **미결** |
| 운영 | 외부 포트를 열지 않고 NaruWorks 도메인 뒤에서만 접근한다. 호스트명 공개는 연동 시험이 끝난 뒤 마지막에 한다 | **확정** (Litpage 계획) |

## 3. 온보딩 절차 (제안)

1. 사용자가 필요한 오픈소스를 신청한다(또는 운영자가 후보를 정한다).
2. 라이선스와 보안을 검토한다. 이슈 형태로 기록한다.
3. 코드를 가져와 수정할지(포크/복사), 설정으로 연동할지 정한다. Litpage는 코드를 `services/litpage`로 가져와 수정하는 방식을 택했다.
4. 인증, 상단 바, 드라이브 저장을 연동한다.
5. 로컬에서 로그인, 로그아웃, 회원 정지 시나리오를 시험한다.
6. 운영 Keycloak 클라이언트를 등록하고 도메인을 공개한 뒤 카탈로그에 올린다.

## 4. 현재 인증 연동 구조

각 서비스가 Keycloak에 클라이언트로 등록하고 직접 OIDC 로그인을 한다. 로그인이 끝나면 서비스는 토큰을 한 번 확인하고 자기 쿠키 세션을 만들어 쓴다.

```text
브라우저 -> Naru 백엔드(Spring)  : Keycloak 로그인 후 JSESSIONID 발급
브라우저 -> Litpage(Node)        : Keycloak 로그인 후 lit_session 발급
```

가입은 Naru 백엔드가 맡는다. 초대 코드(`/join?ref=`)로 들어와 약관에 동의하면 `PENDING`으로 저장되고, 관리자가 승인하면 `APPROVED`가 되며 Keycloak에 `member` 역할이 붙는다. 초대 없이 로그인한 비회원의 Keycloak 사용자는 삭제한다. 자세한 내용은 [중앙 인증 설계](idp-keycloak-architecture.md)에 있다.

## 5. 문제와 결정

### 문제

한 사람의 로그인 상태가 세 군데에 따로 있고 수명과 로그아웃이 서로 연결되어 있지 않다.

| 상태 | 위치 | 끝나는 때 |
| --- | --- | --- |
| Naru 앱 세션 | Naru 백엔드 | 7일 미사용 또는 Naru 로그아웃 |
| Litpage 세션 | Litpage 쿠키 | 7일 또는 Litpage 로그아웃 |
| Keycloak 로그인(SSO) | Keycloak | 로컬 realm 값은 30분 미사용 또는 최대 10시간. 운영 값은 **미확인** |

그 결과 Naru에는 로그인되어 있는데 Keycloak 로그인이 먼저 끝나 Litpage에서 다시 로그인하게 되거나, 한쪽에서 로그아웃해도 다른 쪽 세션이 남는다. 세션이 없다는 사실만으로는 비회원인지 알 수 없다. 이슈 [#80](https://github.com/HoBaeBang/naruworks-platform/issues/80)에서 정리한다.

### 확정

- 로그아웃은 전체 로그아웃으로 한다.
- Keycloak SSO 유지 시간(`SSO Session Idle`)을 7일로 맞춘다.
- 서비스는 앞으로 10개 이상으로 늘 수 있다고 전제한다.

### 제안

- **회원 정지 반영 목표**: 정지 즉시(수 초)를 목표로 하고, 최악의 경우 5분 이내로 한다. 정지할 때 Naru 백엔드가 Keycloak에 사용자 로그아웃을 요청하고, Keycloak이 서비스에 알리는 Back-channel logout으로 세션을 끊는다. 5분은 Access 토큰 수명(로컬 값 5분)이다.
- **SSO Max 시간**: Idle이 7일이어도 Max가 짧으면 매일 써도 주기적으로 다시 로그인한다. 30일 정도를 제안한다. 값은 정해지지 않았다.
- **새 서비스는 공통 게이트를 표준으로 검토**: 서비스마다 로그인, 세션, Back-channel 엔드포인트를 직접 구현하면 10개가 되었을 때 같은 작업을 반복한다. 앞단에 인증 게이트(oauth2-proxy 같은 인증 프록시, 또는 Cloudflare Access)를 두고 세션과 로그아웃을 한 곳에서 처리하는 방식을 검토한다. 기존 두 앱(Naru, Litpage)은 갈아엎지 않는다.
- MCP나 API처럼 토큰으로 직접 들어오는 경로(Litpage MCP)는 게이트 예외로 두고 직접 OIDC로 검증한다.

### 게이트 구조의 흐름 (제안)

게이트가 Keycloak 로그인을 맡고 `*.naruworks.com` 쿠키 하나를 발급한다. 토큰은 게이트가 보관해 갱신하고, 서비스에는 짧은 수명의 Bearer 토큰을 붙여 전달한다. 서비스는 서명만 검증하고 `sub`로 자기 회원 정보를 찾는다.

| 상황 | 흐름 |
| --- | --- |
| 가입 | 초대 링크의 코드를 임시 저장 → 로그인 → `member` 역할이 없으므로 가입 경로만 통과 → 약관과 신청으로 `PENDING` → 관리자 승인 → `member` 역할 부여 |
| 평소 로그인 | 게이트 쿠키 없음 → Keycloak 로그인(SSO가 있으면 화면 없음) → `member` 확인 → 쿠키 발급 → 서비스로 전달 |
| 캘린더에서 Litpage 이동 | 같은 게이트 쿠키를 보내므로 로그인 화면이 없다 |
| 로그아웃 | 어느 서비스든 게이트의 로그아웃으로 이동 → 게이트 세션과 Keycloak 로그아웃 → 모든 서비스가 동시에 로그아웃 |
| 회원 정지 | `member` 역할 제거와 Keycloak 사용자 로그아웃 → 게이트 세션이 끊김. 이미 나간 토큰은 최대 5분 |

### 미결/미확인

- 게이트 도구 선택(직접 운영 vs Cloudflare Access)과 Cloudflare Access의 요금과 사용자 수 제한: 확인하지 못했다.
- 초대 코드를 가입 도중 게이트 로그인을 거쳐 전달하는 방식이 선택한 도구에서 되는지.
- Naru 백엔드가 요청마다 회원 상태(정지 여부)를 DB에서 확인하는지.
- Spring Security의 Back-channel logout이 현재 버전에서 바로 되는지.
- Naru 프론트와 API가 모두 `*.naruworks.com` 아래에 있어 쿠키 공유가 가능한지.
- 운영 Keycloak의 실제 SSO와 토큰 수명.

## 6. 드라이브 연동 방향

- 오픈소스 서비스의 결과물을 나루 드라이브에 저장한다. 모든 회원은 5GB를 무료로 쓰고 그 이상은 요금제로 제공한다.
- 파일 형식을 기준으로 이어서 작업할 수 있게 한다. 더 좋은 서비스로 바꿔도 같은 확장자를 지원하면 같은 파일을 연다.
- 현재 드라이브는 폴더 조회·생성, 이름 변경, 이동까지 구현되어 있다. 오픈소스 서비스가 드라이브에 저장하는 방식(API 연동, 파일 시스템 마운트 등)은 **미결**이다.

## 7. 적용 사례: Litpage

노션형 문서 서비스로 [Litpage](https://github.com/litmers-dev/litpage)(MIT)를 첫 오픈소스로 연동하고 있다.

- 코드를 `services/litpage`로 가져와 수정했다. 원본 대비 수정 목록과 환경변수는 `services/litpage/NARU.md`에 있다.
- 로그인은 Keycloak OIDC 하나로 바꿨고(이메일 코드, 비밀번호, 2단계, 패스키, 데모 제거), 세션은 7일이다.
- 상단에 NaruWorks 바를 붙였고 로그아웃은 ID 토큰(`id_token_hint`)을 보내 Keycloak 확인 화면을 건너뛴다.
- 아직 남은 일: MCP를 Keycloak Bearer 인증으로 교체, 외부 공유를 공개 링크만으로 제한, compose 서비스와 realm 클라이언트 추가, 실제 도메인 시험, 드라이브 연동.
- 운영 배포 전에 운영 Keycloak에 `member` 역할(#73)과 `litpage` 클라이언트가 있어야 한다.
